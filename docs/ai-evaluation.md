# AI evaluation

AI evaluation is the systematic assessment of a model or AI-enabled system against intended tasks, operating conditions, and potential harms. A useful evaluation makes the claim being tested explicit and gathers evidence relevant to real use; a single score rarely captures the full behavior of a system.

## Evaluate the system in context

Define the users, tasks, success criteria, and unacceptable outcomes before testing. Use representative cases, including difficult and failure-prone examples. Assess the complete workflow where possible: model behavior, supplied context, tools, user interaction, and review all affect outcomes.

Combine quantitative measures with qualitative inspection when appropriate. Document the evaluation setup and limitations so results can be interpreted and repeated. Re-evaluate after material changes to models, prompts, data, tools, or deployment conditions, and monitor for changes in actual use.

## Case note: calibrated, and saying almost nothing

The section above asks that tasks and success criteria be defined before testing and that the setup and its limitations be documented so a result can be repeated, and the page opens by saying that a single score rarely captures a system. [applied-statistics-for-AI-engineers](https://github.com/dermot-r-cochran/applied-statistics-for-AI-engineers), the repository the [evidence page](evidence.md) lists for this topic, teaches those statistics on a system that does not exist, and since 26 October 2026 (pull request #53) has held one real model to them: the keeper model in `examples/`, added at the author's direction, in the words its `CLAUDE.md` quotes, "as an example of a delegate model generated and trained using an LLM".

**What was tried.** A language model, in a coding session on 25 and 26 October, chose the label (a frame is kept if it was published or kept as a master), the features (ISO, shutter speed and focal length on log scales, aperture, a sharpness and a brightness score, a flag for a missing ISO, and each frame's sharpness and brightness percentile within its own outing), the validation (every outing held out in turn, so no frame is scored by a model that saw its outing) and the measures, and wrote and ran the code, `examples/keeper-model.js`, a logistic regression with no dependencies, solved by Newton's method so that every run gives the same numbers. It did not supply the labels. The 41 keeps among Reference Set 2's 12,713 frames from 33 outings, a base rate of 0.32%, are the photographer's own decisions, which the page `examples/keeper-model.md` calls "the condition that makes a delegate model worth more than the model that built it". The results are read against three comparisons: chance, the trivial model that gives every frame the base rate, and the one obvious feature, raw sharpness, ranked alone.

**What the record says happened.** Across outings the model is calibrated and uninformative, and the page's own words for the result are "Calibrated, and saying almost nothing": mean prediction 0.33% against 0.32% observed, a calibration error of 0.00183 over ten quantile bins, a Brier score of 0.00322 against 0.00321 for always saying the base rate, a ROC AUC of 0.53 against 0.5 for chance, and a most confident 1%, 127 frames averaging 1.37% predicted, that held none of the 41 keeps. One score would have called it well calibrated; the course's Lesson M exam names the trap, "A constant score equal to the base rate has zero ECE and no use." Asked the narrower question the page then puts, which frames of this outing are worth a first look, a 5% shortlist within each outing finds 9 of the 41 keeps against 2 by chance and 3 for sharpness alone (11 and 13 at 10% and 20%, against 6 and 11 for sharpness; brightness alone finds 1), with the Wilson interval on 9 of 41, about 0.12 to 0.37, beside it and the clustering by outing named. The page records one forking path, two feature sets tried and this one kept after the other's results were seen, and says to read the margins "as a little optimistic". Its verdict goes no wider than the test: "On this evidence the keeper model is useful as a per-outing first sort. It has not earned the right to say how likely any frame is to be kept." The setup is stated far enough to re-run (L2 penalty, `C = 1`, intercept unpenalised, no class weighting, standardised features), and CI holds the prose to the run: `node examples/keeper-model.js --check`, a step of `.github/workflows/ci.yml` since the same pull request, fails if the page does not quote one of the figures it pins, and the README's proof list names it beside the claim that "the keeper model's figures on its own page are the ones a run produces". Two days later (pull request #54, 28 October) the site's own account of what is real caught up, because its case page had still said that nothing scored these frames; it now names the model and says it "is not a reviewer in the sense above". Two things the record does not support. The check is narrower than the sentence that names it. It pins sixteen figures by looking for each as a string anywhere on the page, and six of the summary figures the run prints are not among them, besides the decile table, which the page leaves to the run: the count of keeps and of outings, sharpness at 10% and 20%, brightness at 5%, and the number of keeps in the top 1%, the zero behind the page's "held none of the keeps". A change that moved that count would almost certainly fail the check on the figures beside it, and the sentence could be left standing when the prose was brought back into line. And the page places the forking path for the feature set in the order of events but not the measures: whether the per-outing shortlist, the one measure on which the model clearly beats its baselines, was chosen before the cross-outing result was seen or after it, the page, the pull request and `CLAUDE.md` do not say. The section above asks for the criterion before the test; here the record is silent rather than contrary.

**What changed as a result.** The repository that teaches evaluation statistics on a synthetic system now carries, beside the Reference Set 3 rules its exercises score, one evaluation of a real fitted model, read the way its lessons ask: more than one score, set against baselines a reader could have guessed, an interval on the small count, the clustering named, the one choice made after looking declared, and a verdict no wider than the test that earned it. The page's own close is that the builder's fluency says nothing about the delegate's worth, and that a better model "would need better evidence, not more fitting", the subject labels of Reference Set 3 or features read from the images. That next evaluation is work for that repository, and no issue there records it yet; its record would belong here, as would a check that pins the top-1% count behind the page's "held none of the keeps". Everything above describes the repository as it stood on 8 November 2026.

## Questions to ask

- What specific capability or risk does this evaluation address?
- Are cases representative of the intended users and conditions?
- What errors matter most, and how are their impacts weighted?
- What does the evaluation not establish?
- What evidence would lead us to change, limit, or stop deployment?
